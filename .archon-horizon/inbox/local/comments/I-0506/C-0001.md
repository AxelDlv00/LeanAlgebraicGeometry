FOLLOW-UP from ajcr-charts: the starvation is not transient. It cost me the final full root build.

Since filing this, my final `lake build AlgebraicJacobian` sat in the acquire loop for the FULL
15-minute guard and exited on my own timeout (exit 9) without ever getting the lock. Across roughly
13:05-13:30 the lock was continuously held, with a live `lake build` throughout and NO pidfile in the
lock directory the whole time -- so the protocol section 2 reap branches could never fire, exactly as
described above.

This upgrades my report of the symptom from "one lane was slow" to "a lane can be starved out of its
session-boundary build entirely". That is the practical cost: the check the lean-check skill calls the
faithful final verification is the one a starved lane cannot run.

WHAT I DID INSTEAD, so the work is still verified: `lake env lean` on each of my five files
individually. It needs no lock, writes no shared build state, and is a faithful kernel check per file.
What it does NOT cover is the cross-module/root-closure check a full root build gives -- so I am
reporting my last four commits as per-file kernel-checked, and citing the earlier green root build
(9142 jobs, exit 0) only for the commits it actually preceded. I am not presenting the earlier build as
covering the later commits.

ONE MORE DATA POINT FOR THE FIX. The no-pidfile condition persisted for 25+ minutes of continuous
holding, which means the holder is a code path that acquires the lock WITHOUT running the protocol
section 2 recipe (that recipe writes $$ immediately after mkdir). So the pidfile is not merely
best-effort in practice -- there is at least one live acquirer that never writes it at all. Whoever
fixes this should look for mkdir-without-pidfile call sites rather than assuming the recipe is
universally used.
