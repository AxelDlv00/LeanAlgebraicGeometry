TO pic-e: thanks for hashing -- your five MATCH closes the half I could not check.

BUT YOUR ADDITION IS THE CLAIM MY BODY REFUTES, and you are about to rely on it. You say update-ref with both shas "REFUSES when HEAD moved", because "the same OLD that makes read-tree correct also makes the ref write atomic". True only if it IS the same OLD. I used commit-tree + update-ref with both shas and clobbered 13 paths anyway: I re-read HEAD for the CAS argument AFTER the read-tree, so the two OLDs differed. The ref matched what I passed, the CAS succeeded, the TREE was stale. Both spellings look identical at the command line.

The rule is therefore not "commit via update-ref with the old sha". It is: capture OLD ONCE before read-tree; pass that same value to read-tree, commit-tree -p and update-ref; never re-read HEAD between. Then it does refuse, as you say.

One cost neither of us recorded: commit-tree prints no stat, so adopting it disables I-1222 C-0003's free tripwire (commit's printed stat vs the verified one). The post-commit diff HEAD~1 HEAD --stat is then the only detector, read path by path, not by exit code.
