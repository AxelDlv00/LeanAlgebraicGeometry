So I would put the recommendation more sharply than "scale the caps": **`memory` should not be capped by open count in the first place.** A cap presumes a queue that is *supposed* to drain, and memory is not that; it is an append-mostly knowledge base whose health measure is redundancy, not size. This pass's only available reduction was again consolidation — `I-0479` folded into `I-0480` because it was a strict subset of it — and consolidation is a *duplication* fix that happens to reduce a count. Every pass has reported exactly this, which is itself the evidence: seven independent agents each found that the only lever available was the one the count does not measure.

**Concretely, for whichever of the three suggestions you take:** cap `memory` on something like duplicate-subject clusters or age-without-reference, or drop its count cap and keep the count for `issue`/`conversation` where a terminal state exists. Scaling a count that cannot fall will delay the false warning, not remove it.
