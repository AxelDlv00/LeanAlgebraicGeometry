THE FILTER, AT SOURCE — so the human can judge whether this is a defect or an intended rule (janitor hygiene pass, task `ajc-truth`, run 0054). Leaving this item OPEN: it is addressed to you and is a design question, not a hygiene problem.

The rule is `reaches_horizon` in `Archon-Horizon/src/archon_horizon/core/inbox.py:191`, and it decides visibility in this precedence:

1. `scope.projects` non-empty and not containing your project -> hidden. This correctly hides the three Rebuild-scoped items (`I-0144`, `I-0354`, `I-0367`).
2. owner task set and not yours -> hidden (not in play here; all five have `owner_task: null`).
3. audience empty or containing `horizon` -> visible.
4. otherwise `project:<yours>`, `task:<yours>`, `run:<yours>` -> visible.
5. **last resort:** `metadata.provenance.task` or `.run` equals yours -> visible.

So a `--to human` item reaches step 5 and is listable only by **the team that filed it**. That is the whole mechanism behind the two items that matter: `I-0372` (filed by `ajc-optimize`) and `I-0346` (filed by `ajcr-w4-rep-free`).

**Two observations for your decision.** First, the rule looks like an artifact rather than an intent: step 5 exists so a team can follow replies to a DM it sent, and human-addressed items get team-privacy as a side effect of that fallback. Second, the counting path does not apply this filter at all, which is why the warning says 43 and the list shows 39 — measured again this pass, with the store at 44 open / 43 non-protection.

If the intent is that a human-addressed item scoped to a project should be readable by any agent working that project — which I think is right for a DECISION item, since acting correctly requires reading it — the smallest fix is to treat `audience: human` as visible to Horizon on a matching project scope, and to run the health count through the same predicate as the list so the number is actionable for the team receiving it.
