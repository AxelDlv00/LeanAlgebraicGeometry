## What `I-0520` adds: starvation is real, not just slowness

Measured 2026-07-28, 13:05-13:41: the AJCR mutex `/tmp/claude-1001/ajcr-locks/lake.lock` was held essentially continuously for ~35 minutes. **Two** separate attempts at a final `lake build AlgebraicJacobian` exited on the lane's own lock guard (15 min, then 9 min) without ever acquiring. A lane can therefore be starved out of its session-boundary root build entirely.

## Two holder shapes, and neither is reapable

- **~13:05-13:30 — no pidfile in the lock directory while a live `lake build` ran.** Both reap branches are unreachable: the `kill -0` branch needs a pid, and the "no live build AND >15 min" branch is false because a build *is* live (possibly another project's). Do **not** reap; you cannot prove death.
- **~13:31-13:41 — pidfile present, holder alive.** Legitimate long build. Obviously do not reap.

So the lock can be unreapable-but-blocking for a long time, and waiting is correct in both shapes. Budget for it rather than treating a blocked build as a hang.

## The fallback that works, and its exact limit

```
lake env lean AlgebraicJacobian/Picard/<File>.lean   # per file, exit code is meaningful
```
Needs no lock, writes no shared build state, and is a faithful **kernel** check for that file (LSP diagnostics are not a substitute). What it does **not** give is the cross-module/root-closure check a full `lake build AlgebraicJacobian` gives. So report per-file checks *as* per-file, and never cite an earlier green root build as covering commits made after it — the same reporting rule this item already states.

## One clue for whoever repairs the lock

The no-pidfile window lasted 25+ minutes of continuous holding, so at least one live acquirer takes the lock **without** the documented recipe (which writes `$$` immediately after `mkdir`). Look for `mkdir`-without-pidfile call sites rather than assuming the recipe is universal. `I-0502` carries the human-facing report.
